# kanban-desktop 测试体系架构方案

> **取代标注（2026-11-06）**：本方案已由 spec #23（issue，三执行类模型 + 迁移 + 接线）+ `docs/testing.md`（通用测试规范）+ `docs/adr/0002-test-architecture.md`（决策记录）落地实施。本文保留作调研依据；与 spec #23 冲突之处**以 spec 为准**（已知冲突举例：本文 §4.1 推荐根级 `vitest.workspace.ts` 与 Playwright 放 `tests/e2e/`，实际落地为各包独立 vitest 配置 + Playwright 留在 `apps/desktop/e2e/`）。

> 适用项目：`kanban-desktop`（Electron + React + pnpm workspace monorepo）  
> 目标：解决源码与测试文件混杂问题，建立清晰、可扩展、适配 Electron 双进程架构的测试体系。  
> 核心策略：**按归属分层，按环境分治；单元/组件测试共置，集成/E2E 测试分离。**

---

## 1. 背景与问题

当前项目中实际代码文件与测试文件放在同一文件夹中混杂，随着功能增加会出现以下问题：

- 源码目录中同时存在业务代码、单元测试、集成测试、E2E 测试和测试数据，职责不清。
- Electron 主进程与渲染进程的测试环境不同，但目录上没有体现边界。
- 跨进程、跨模块的集成测试与普通单元测试混在一起，运行和排查成本高。
- monorepo 下 `apps/desktop` 与 `packages/*` 的测试归属不明确，容易形成“哪里方便放哪里”的杂乱结构。
- CI 中难以按测试类型、按应用/包、按运行环境分别执行。

本方案的目标不是简单地把所有测试搬到某个 `tests/` 目录，而是建立一套**有边界、有分层、可配置、可迁移**的测试架构。

---

## 2. 设计目标与原则

### 2.1 设计目标

1. **消除混杂感**：源码目录只保留与源码紧密相关的单元/组件测试。
2. **尊重 Electron 架构**：主进程、渲染进程、共享代码分别使用合适的测试环境。
3. **明确测试归属**：`apps/desktop` 的测试归 desktop，`packages/*` 的测试归对应包。
4. **支持分层运行**：单元、组件、集成、E2E、冒烟测试可以独立运行。
5. **适配 pnpm workspace**：根目录可统一运行，也可按应用/包/环境分别运行。
6. **便于渐进迁移**：不需要一次性重构所有文件，可分阶段落地。

### 2.2 核心原则

- **单元/组件测试共置**：`*.test.ts` / `*.test.tsx` 紧邻被测源码，修改代码时测试就在旁边。
- **集成/E2E 测试分离**：跨进程、跨模块、完整产品流程的测试集中到所属应用或包的 `tests/` 目录。
- **按归属分层**：测试放在它所属的 `apps/*` 或 `packages/*` 内，不建立根级“大杂烩 tests”。
- **按环境分治**：主进程使用 Node 环境，渲染进程使用 jsdom 环境，共享包按实际运行环境配置。
- **文件名表达测试类型**：单元/组件用 `*.test.ts(x)`，E2E 用 `*.spec.ts`，避免类型混淆。

## 3. 调研结论摘要

调研了多个 Electron、React、monorepo 和工具链项目的测试组织方式，结论是：**“全分离”和“全共置”都不是最优解，成熟项目普遍采用分层混合策略。**

| 项目/类型 | 关键做法 | 对本项目的启示 |
| :--- | :--- | :--- |
| VS Code | 单元测试共置，集成测试集中在 `src/test/integration/` | 轻量单元测试跟随源码，重集成测试集中管理 |
| Electron | 测试套件放在独立 `spec/`，并作为独立 Node 项目管理 | 大型 Electron 项目需要隔离测试依赖和环境 |
| React | 测试放在相关 `__tests__` 文件夹中 | 组件测试适合与组件就近组织 |
| Vue.js | 存在独立 `tests/` 与共置两种实践 | 没有唯一标准，关键是项目内保持一致 |
| Next.js | 支持 `app/` 内共置，也支持根级 `__tests__`，E2E 放顶层 `e2e/` | E2E 应独立于单元测试目录 |
| Tabularis | 严格分离 + 镜像 `src/` 结构，`src/` 禁止测试文件 | 分离模式适合需要强隔离的项目 |
| Crossmint SDK | “Tests live with their app”，按测试类型分 `e2e/`、`api/`、`sdk/`、`smoke/` | 测试应归属应用，并按类型分层 |
| Agenta | monorepo 内各组件标准化 `unit/`、`integration/`、`acceptance/` | monorepo 需要统一的测试分类规范 |
| Automaker | Server 测试在 `apps/server/tests/`，E2E 在 `apps/ui/tests/` | 按应用/包边界分离测试，与 pnpm workspace 契合 |
| Uptime-Watcher | 为渲染进程、主进程、共享代码分别建 Vitest 配置，Playwright 做 E2E | Electron 项目应按运行时环境隔离 Vitest 配置 |
| Unfour | 单元/组件共置，跨模块集成、桌面冒烟、E2E 放独立 `tests/` | 推荐“非对称混合”布局，避免根级大 `tests/` |
| aily-blockly | `tests/` 放 Node 单元/模块集成，`tests/electron/` 放 Electron 测试，`e2e/` 放验收 | Electron 测试需要明确边界，生产目录不放测试夹具 |

**结论：** 对 `kanban-desktop` 最合适的方案是：

> 在 `apps/desktop` 和 `packages/*` 的边界内，采用“单元/组件共置 + 集成/E2E 分离 + Vitest Workspace 按环境分治”的分层混合架构。

---

## 4. 推荐总体架构

### 4.1 核心决策

1. **`src/` 内只放单元测试和组件测试**，命名统一为 `*.test.ts` / `*.test.tsx`。
2. **`apps/desktop/tests/` 放 desktop 应用的跨边界测试**：集成测试、E2E、冒烟测试、测试夹具、测试环境 setup。
3. **`packages/*/tests/` 放该包自己的集成测试**；包内单元测试仍然共置在 `src/` 旁边。
4. **根目录使用 `vitest.workspace.ts` 聚合不同环境**：`desktop-main`、`desktop-renderer`、`packages` 分别配置。
5. **E2E 使用 Playwright**，配置放在 `apps/desktop/playwright.config.ts`，测试文件放在 `apps/desktop/tests/e2e/`。
6. **不建立根级“大而全”的 `tests/` 目录**，避免测试归属模糊。
